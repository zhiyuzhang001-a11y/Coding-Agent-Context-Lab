# Smart Read 长期约束清单

最后更新：2026-08-15

## 1. 核心目标

Smart Read 的目标不是“理解整个代码库”，而是：

> 在统一且严格的 Token Budget 下，用尽可能少的探索，取得足以解决当前任务的上下文与源码证据。

这份清单用于防止 Smart Read 逐渐变成完整静态分析器、无限扩张的知识图谱，或自身成本高于节省量的复杂路由系统。

Smart Read 自己也必须遵循“稀疏、高价值、可解释”的路标原则：模块要少，信号要少，每个信号都要能证明贡献。

当前产品主线的最高设计原则：

> Smart Read 不替代 Codex 的语义判断，不要求 Codex 驾驶导航器；只负责在源码和搜索结果进入模型前完成切片、压缩、去重和预算控制。任何优化失败都应可观测地回退到 Native 行为。

## 2. 每次开发前的五问

任何准备进入 Smart Read 核心的新功能，都必须先回答：

1. 这个功能会不会减少搜索空间？
2. 它会不会增加 Smart Read 自己的 Token、计算、存储或延迟成本？
3. 它解决的是 Ranking 问题，还是 Graph 问题？
4. 有没有真实任务和 baseline 能证明提升？
5. 如果删除这个功能，结果会明显变差吗？

准入规则：

- 不能减少搜索空间的功能，默认不进入核心。
- 自身成本高于可验证收益的功能，默认拒绝或只保留为实验。
- 无法判断问题属于 Ranking 还是 Graph 时，先补诊断证据，不先调权重或加边。
- 没有真实任务与 baseline 的功能，只能标记为实验性。
- 删除后结果没有明显变差的功能，不应留在 Smart Read 核心。

## 3. 不可绕过的约束

### 3.1 范围与架构

- 不把 Smart Read 做成完整静态分析器。`calls`、`inherits`、`references` 只覆盖对导航有价值的高收益子集，不追求语言语义 100% 精确。
- 当前任务导航与长期记忆分层：M2 解决“现在去哪里找”，M3 才解决“过去为什么这样设计”。两者不能提前混成一个系统。
- 每个 Milestone 必须明确写出“不做什么”，防止 scope creep。
- 不过早加入 embedding。只有结构图与 Feedback 出现有证据的语义 Recall 瓶颈后才进入实验；进入核心前必须完成消融实验。
- 达到 Milestone 验收指标后冻结一个可复现版本，保留 benchmark 结果，再开始下一轮架构变化。

### 3.2 稀疏图与导航

- 每新增一种 Edge，必须至少证明它改善了以下一项：target recall、导航 steps、Token 消耗或错误停止率；同时不得造成不可接受的回归。
- 图越密不代表导航越好。只保留高价值、可解释、低成本的关系边。
- Graph expansion 必须限制 hop、fan-out 和总预算；不得退化为整仓库遍历。
- 不同 Edge 必须有独立的成本、可信度与扩展优先级。direct call 通常应高于模糊 reference，但最终以 benchmark 为准。
- 数据库存地图、标识符、关系、摘要和必要元数据；不保存不必要的源码正文。源码证据按需回源读取。
- 每次选择 Marker 应能说明“为什么选择它”，包括主要得分信号、关系来源和预计读取成本。

### 3.3 先分类失败，再修改系统

失败至少分为四类：

- **Ranking 失败**：目标存在且可达，但候选排序差，未在预算内选中。
- **Graph 失败**：相关起点存在，但在允许的 Edge、hop 和 fan-out 下无法到达目标。
- **Evidence 失败**：已定位正确 Marker，但源码截取、范围覆盖或回源读取未提供足够证据。
- **Stop 失败**：系统在仍有高价值候选时提前停止，尤其是 `low_expected_gain` 导致的 false negative。

不得用增加 Edge 掩盖 Ranking 问题，也不得只调 Ranker 权重掩盖地图缺路。

### 3.4 Feedback 与停止策略

- 每次读取应产生结构化 Feedback，并携带证据来源和置信度。
- 第一次读错节点时，不能让低置信度关键词持续自强化。系统需要负反馈、降权或撤销机制。
- `low_expected_gain` 是重点风险指标：既记录其节省的 Token，也记录它造成的错误停止。
- 所有任务必须有明确 `stop_reason`；未知停止或预算外退出视为缺陷。

### 3.5 统一预算与正确性

- Hard Token Budget 是系统级约束。Ranker、Graph expansion、Skill、CLI、插件和源码读取不得各自建立可绕过的预算。
- 防止重复读取不仅判断 Marker 是否已读，还应逐步支持源码范围覆盖：较大已读范围可以覆盖其内部的较小请求。
- 缓存不得牺牲正确性。文件 hash 变化、删除、重命名、截断内容和强制重读都必须正确失效或更新。
- Smart Read 自身的 routing、Feedback、索引和模型调用成本必须计入总成本。为节省 1000 Token 而先花 1500 Token 路由属于负优化。
- CLI、Skill、Plugin 与源码实现必须保持一致；发布验收要验证安装后的实际版本，而不仅是工作区源码。

### 3.6 透明优化与失败开放

- 透明优化是否成立，以模型最终可见输入为准，不以 Hook、缓存或压缩器“执行成功”为准。
- Optimizer 只能接管经过明确验证的工具路径；未知命令、复杂 shell、测试、构建和脚本默认 passthrough。
- Context Optimizer 故障必须 fail-open，不得显著破坏 Native Codex 的任务能力；该规则不覆盖安全策略或权限控制。
- fail-open 必须可观测。至少区分 `optimized`、`passthrough_unsupported`、`fallback_optimizer_error` 与 `fallback_budget_or_timeout`，并记录原因。
- 白名单门控用例发生 fallback 时不能计为优化成功，也不能混入节省比例。
- 缓存命中不等于模型 Token 节省。只有能够证明正文已经对当前模型上下文可见，才可用稳定 Evidence handle 代替重复正文；跨 session、上下文压缩或证据不可见时必须允许重放。

## 4. 统一指标口径

Token 报告必须至少区分：

- **定位 Token**：用于搜索、候选比较和导航的上下文。
- **源码证据 Token**：最终实际读取并交给 Agent 的源码。
- **Navigator 开销**：路由、Feedback、图扩展、摘要或模型判断本身的 Token。
- **完整任务 Token**：从任务输入到最终答案或代码变更的全部可计量消耗。

同时记录非 Token 成本：索引时间、查询延迟、存储大小和增量更新成本。

任何节省比例必须明确场景、分子、分母、预算和 baseline。“省 60%”若只发生在代码定位或证据读取阶段，不得表述为完整开发会话节省 60%。

评估不能只看平均值，还要记录最差案例或尾部指标，包括最大无效展开、极端 Token 消耗、错误 stop 和未找到目标。

## 5. Benchmark 与证据要求

至少持续保留以下 baseline：

- 原生 Codex 或等价的普通文件探索流程；
- Static Top-K；
- Navigator；
- Smart Read + Graph。

Benchmark 规则：

- 3 个任务只用于功能验收，不能支持普遍有效的结论。
- 任务集应逐步扩展到几十个真实任务，覆盖有 identifier、无 identifier、跨模块、继承、调用、reference 和错误停止等类型。
- 小型 fixture 验证逻辑；真实大型仓库验证导航是否真正连通。
- Serena 是重要回归样本，但不能成为唯一优化对象。后续应覆盖 Web、CLI、库和 Agent 框架等不同项目结构。
- 自然语言任务仍是高风险区域；样本不足时不得宣称普遍改善。
- 每个真实失败都应进入 benchmark，成为后续版本必须继续通过的 regression case。失败记录优先于只积累成功案例。
- 每次实验保存代码 commit、插件版本、benchmark 版本、预算、参数、完整任务文本和 baseline 结果。

## 6. 数据、历史与隐私

- 不保存完成导航所不需要的源码正文，降低隐私、存储与失效成本。
- Git 是 Decision Memory 的事实来源之一。未来的设计决策记录应尽量关联 commit、diff、测试和 issue，而不只保存模型总结或聊天记录。
- 历史信息只有在能减少未来搜索空间、解释约束或避免重复错误时，才升级为高价值 Marker。

## 7. 功能准入检查单

新功能进入核心前，必须留下以下记录：

- [ ] 要解决的失败案例与失败分类；
- [ ] 减少搜索空间的机制假设；
- [ ] 自身 Token、计算、存储和延迟成本；
- [ ] 真实任务、固定预算与 baseline；
- [ ] 对 target recall、steps、Token 和错误停止率的影响；
- [ ] 删除功能或关闭信号的消融结果；
- [ ] Hard Budget、hop、fan-out 与缓存失效边界；
- [ ] 明确的非目标；
- [ ] CLI、Skill、Plugin 安装态一致性检查；
- [ ] 可复现的版本与实验记录。

## 8. 发布与冻结规则

一个 Milestone 只有在验收标准、旧测试、真实 benchmark、预算约束和安装态一致性全部通过后才能标记完成。

完成后应：

1. 固定 commit、插件版本、benchmark 和参数；
2. 保存成功与失败结果；
3. 更新 `STATUS.md` 与 `PROJECT_PLAN.md`；
4. 冻结该版本，不为无明确失败案例的“再优化一点”继续改变核心架构。

## 9. 最终红线

> Smart Read 不能成为新的“无垠草丛”。如果一个模块、信号或索引不能以真实任务和消融实验证明自己显著缩短了探索路径，它就不属于 Smart Read 核心。
