# 上游项目能力与 Token 节约机制评估

评估日期：2026-08-15

## 评估方法

本评估区分四类成本，避免把“本地索引更快”误报为“模型 token 更少”：

1. **索引成本**：在本地解析、建图和缓存，通常不消耗模型 token。
2. **上下文成本**：实际返回或注入模型的代码、地图和历史 token。
3. **编排成本**：模型选择工具、生成参数、理解结果所产生的轮次与 input/output。
4. **重复发现成本**：跨任务、跨 session 重新理解相同结构、历史和决策。

项目自己的节省数字均标记为上游报告，未通过本项目复现实验前不作为产品承诺。

## Serena

官方仓库：https://github.com/oraios/serena

### 做了什么

- 通过 LSP 或 JetBrains 后端提供符号查找、文件符号概要、引用查找、声明/实现定位。
- 提供按符号替换、前后插入、安全删除和重命名等编辑能力。
- 提供简单的文件式长期记忆。

### 如何减少消耗

它把“grep → 打开整文件 → 找定义 → 再找引用”改为符号级查询，只返回目标符号正文或引用片段。精确编辑也避免为一个函数修改而重发整个文件。

### 对我们的价值

- 最适合充当 **精确证据与编辑 Provider**。
- 可提供结构标记的真实符号位置和关系标记中的引用边。
- 不负责全仓库动态排名，也不会自行决定当前最值得读取的节点；仍依赖 Agent 编排。

### 限制与本项目证据

- MCP 工具描述、语言服务器启动和多轮调用会产生额外编排成本。
- Serena 的 memory 主要是文件读写，不等同于可检索、可失效的历史/决策图。
- 本项目 B009 中两次原生工具结果仅约 498 token，但完整 input 为 70,283，与 M1 的 70,605 接近。因此“符号返回更短”尚未转化为端到端节省。

结论：**保留，作为可替换精确查询后端；不作为 Smart Read 的总架构。**

## Codebase-Memory MCP

官方仓库：https://github.com/DeusData/codebase-memory-mcp

论文：https://arxiv.org/abs/2603.27277

### 做了什么

- 用 Tree-sitter、多阶段关系解析和 SQLite 建立持久代码知识图谱。
- 保存函数、类、调用链、导入、路由、跨服务关系、社区聚类和变更影响。
- 提供结构搜索、调用路径、影响分析、架构概览、源码片段和图查询等工具。
- 使用内容哈希增量更新，并能共享压缩图谱产物。

### 如何减少消耗

它用一个图查询替代多次 grep、文件读取和调用链人工拼接。模型先接收紧凑的节点与边，只有确认实现时才读取源码片段。

论文在 31 个真实仓库上报告：相对文件探索 Agent，约 10 倍更少 token、2.1 倍更少工具调用，但回答质量为 83%，对照组为 92%。这说明节省明显，同时也真实存在结构图遗漏细节导致的质量损失。

### 对我们的价值

- 与 **Relational Marker Provider** 高度匹配。
- 可直接补足当前缺少的调用关系、影响范围、架构聚类和跨文件导航。
- CLI 模式允许我们在自己的单进程流程中调用并转换结果，不必再构造嵌套 MCP。

### 限制

- 默认暴露的工具较多，若全部加入 Agent 工具上下文，会增加 schema 和选择成本。
- 图关系存在解析置信度和语言差异，不能作为编辑前唯一事实来源。
- 上游数字不能直接外推到我们的 Codex 插件；必须使用同任务 A/B。
- 它还提供 ADR 管理，但自动写入决策记录的可信边界不符合我们“确认后才成为事实”的原则。

结论：**最值得做最小 Provider 实验，但只接结构搜索、调用路径和片段定位三个能力；最终代码仍由 Smart Read/Serena核验。**

## Aider Repo Map

官方文档：https://aider.chat/docs/repomap.html

实现：https://github.com/Aider-AI/aider/blob/main/aider/repomap.py

### 做了什么

- 用 Tree-sitter 提取类、函数、签名和引用标签。
- 构建文件依赖图，并通过图排名选择重要标识符。
- 结合当前聊天中提到的文件和标识符动态提高相关节点权重。
- 在活动 token 预算内生成稀疏 Repo Map；官方默认地图预算约 1,024 token，并会根据聊天状态调整。

### 如何减少消耗

它不是等待 Agent 盲读，而是预先提供一张小型全局地图，让模型知道目标大致在哪里；只选择排名最高且能放入预算的结构，而不是发送全部标签。

### 对我们的价值

- 是 **BaseValue + TaskValue + Token Budget** 最直接的算法参考。
- 证明“稳定标签缓存 + 依赖图排名 + 当前任务加权”是一条成熟路线。
- 其思路非常适合 M2a，但 Aider 的实现与自身聊天、模型和缓存系统耦合，不适合直接作为运行时依赖。

### 限制

- Repo Map 通常随请求进入上下文，本身是固定开销；任务很小时可能比直接读取更贵。
- 擅长定位重要符号，不负责历史、决策或完整的任务探索状态。
- 图排名表达的是结构重要性与聊天相关性，不等同于真正的信息增益。

结论：**重点借鉴算法和预算策略，不直接集成整个 Aider。**

## Stacklit

官方仓库：https://github.com/glincker/stacklit

### 做了什么

- 本地使用 Tree-sitter 提取模块、依赖、导出、类型、Git 活跃度、框架和测试提示。
- 生成可提交的 `stacklit.json`、依赖图和可视化页面。
- 可派生约 250-token 的紧凑导航地图，并提供 7 个模块级查询工具。
- 使用 Merkle 哈希避免无关变更触发全量重建。

### 如何减少消耗

把每个 Agent 都要重复进行的“目录扫描和模块定位”提前压缩成一个共享索引。Agent先读取紧凑模块地图，只有相关模块才进一步展开。

### 对我们的价值

- 非常适合作为 **Sparse Navigation Map 的数据形态和增量更新参考**。
- 模块、依赖、导出、活跃度与我们的结构/关系/历史标记一一对应。
- `derive` 的小地图比每次读取完整 JSON 更符合默认上下文预算。

### 限制

- 主要是模块级静态地图，任务相关的动态节点价值和任务状态较弱。
- 上游展示的 token 数是项目自身案例，不代表完整 Agent 会话节省。
- 可选 AI summary 会引入外部模型成本和隐私问题，不应作为我们的默认路径。

结论：**重点借鉴 schema、紧凑派生视图和 Merkle 增量策略；M2a 后再决定是否直接做 Provider。**

## AgentMemory

官方仓库：https://github.com/rohitg00/agentmemory

### 做了什么

- 通过生命周期 Hook 捕获工具观察和会话结果，去重、隐私过滤并压缩为多层记忆。
- 使用 BM25、向量和知识图谱检索，通过 Top-K 与 token 预算在新会话注入相关历史。
- 区分 working、episodic、semantic 和 procedural memory，并支持跨 Agent 共享。

### 如何减少消耗

它减少跨 session 重复解释和重复探索：不是加载全部历史，而是检索相关记忆后按预算注入。项目报告在其示例规模下从 22K+ 降至约 1.9K token；这是上游自报，尚未由本项目验证。

### 对我们的价值

- 与 **Historical Marker、Decision Marker 和 Task Handoff** 高度相关。
- 可参考去重、生命周期、混合检索、时间衰减和 session summary。

### 限制

- 它解决的是历史上下文，不解决当前仓库首次符号定位。
- 自动捕获和 LLM 压缩可能保存错误推断、敏感信息或过时事实。
- 53 个 MCP 工具和多 Hook 对当前 MVP 过重；默认注入约 2K token 对短任务可能是净增加。
- 决策标记需要人工/测试证据确认，不能直接照搬“自动记住一切”。

结论：**推迟到 M3；借鉴生命周期与检索，不现在安装或并入核心。**

## Repomix

官方仓库：https://github.com/yamadashy/repomix

### 做了什么

- 将仓库合并为 XML、Markdown、JSON 或纯文本等 AI 友好格式。
- 提供文件和目录 token 统计、include/ignore、Git 历史/差异、输出预算与敏感信息扫描。
- `--compress` 使用 Tree-sitter保留类、函数和接口结构，省略实现细节。

### 如何减少消耗

通过过滤文件、删除低价值文本、结构压缩和预算检查减少一次性打包体积；也可通过 MCP 在打包结果中增量搜索。

### 对我们的价值

- 最适合做 **token 计数器、数据集打包器和实验 baseline**。
- per-file inclusion level 可以启发动态分辨率，但其策略主要按 glob 配置，不是任务导航。

### 限制

- 即使压缩后，核心仍是把较大的静态包交给模型；不能替代动态 Top-K 路标和任务状态。
- 删除实现细节后不能直接用于可靠编辑。

结论：**保留为测量与基准工具，不作为在线导航核心。**

## 它们怎样映射到我们的架构

```text
Aider Repo Map ─────→ 路标排名与动态 token 预算思想
Stacklit ───────────→ 稀疏基础地图、模块 schema、增量更新
Codebase-Memory ────→ 关系标记 Provider、调用链和影响分析
Serena ─────────────→ 精确符号/引用证据与安全编辑 Provider
AgentMemory ────────→ 历史/决策/跨 session 生命周期参考
Repomix ────────────→ tokenizer、压缩基线和实验数据打包
```

## 推荐采用顺序

1. **现在借鉴 Aider + Stacklit**：完成我们自己的 Marker/Edge schema、图排名、紧凑派生视图和增量索引。
2. **随后小范围试接 Codebase-Memory CLI**：只映射 `search_graph`、调用路径和源码定位结果，避免一次暴露全部 MCP 工具。
3. **继续保留 Serena 原生最小后端**：用于核验目标实现和引用，不再做嵌套 MCP。
4. **使用 Repomix 校准 token 与构造基线**。
5. **M3 再研究 AgentMemory**：只吸收有证据、可失效的历史和决策记录。

## 接纳门槛

任何上游 Provider 进入默认路径前，必须在相同真实任务上满足：

- 答案与修改质量不下降；
- 编辑前仍能回到当前源码证据；
- 完整会话 input 至少降低 20%；
- 工具轮次和总延迟不明显恶化；
- 索引能够增量失效且默认不上传源码；
- 只暴露完成任务所需的最小工具/数据面。
